# Instance-wide provider model selection

Model selection is stored once per owner/provider. Accounts only store exclusions, and later accounts use the same provider selection automatically. Selection, each account's actual discovery result, and per-computer access withdrawal are separate policy inputs. Account identity, holder custody, secrets, OAuth sessions and enablement are unchanged.

Owner/Admin commands `ctox.workjet.providers.models.select` and `ctox.workjet.providers.models.exclude` use the normal authenticated Business OS command plane, IntegrationsManage permission, durable domain-effect admission and optimistic policy/account revisions. No caller endpoint, credential or consumer identity is accepted. A provider selection is initially unconfigured; live discovery by itself never grants model use. Adding a choice requires a fresh actual GET /models observation on an enabled, configured owned account of that provider. Removing existing choices works during an outage. Exclusions may only add names actually observed on the exact account; removing exclusions is independent of provider reachability.

The instance list projects shared selection, per-account exclusions and their intersection with the account's last real model list. Last-known IDs remain visible during a transient failure with the existing catalog freshness/failure metadata. They do not prove inference, capacity or routing authority. A missing model only loses that model's eligibility; the account and its other models are not cooled down or disabled.

The native `with_consumable_model` seam takes Architecture's sealed, possession-bound original-consumer context, re-enters current identity/enrollment/policy fences, and binds the exact logical account, account/policy revisions, selected model and successful catalog timestamp. A model must appear in the account's current live list, be selected for the provider and remain unexcluded. Default account access for enrolled computers is preserved, subject to explicit withdrawals for the actual consumer. The context contains a holder-private selector and cannot be serialized. This is eligibility, not execution authority, a signed forwarding grant or completed holder dispatch. Native request adapters can capture this private context and re-enter it after awaits; identity, policy, catalog and private configuration changes retire the captured binding rather than silently choosing a new account. Callers still require actual task execution authority and must revalidate around awaits and publication. Architecture has confirmed that #508 is transient and there is currently no sealed durable original-computer lease: its follow-up must persist the admitted origin at durable job admission and revalidate current enrollment/device/owner/withdrawal plus execution ownership without requiring the original browser connection to remain open. This context must not replace that missing durable worker/continuation authority.

Tests use exact real IDs from the retained authenticated llm.ctox.dev catalog evidence, not invented models. They cover shared selection and later accounts, account-specific intersections/exclusions, stale/disabled catalog rejection, outage removal, owner/revision conflicts, exact consuming-computer withdrawal, failed discovery/model disappearance without account cooldown, unadmitted/private input rejection, and persistence across store reopen. These are isolated policy tests; they do not claim installed federation acceptance.

This slice depends on CTOX #514 for actual native model observations. Subsequent holder routing, authoritative Sync projection and Workjet consumption use these server-owned facts; no Environment selector is removed ahead of those working paths.
